# AGENTS.md

本文件规定 `Multi-TTS` 仓库中的编码规则、工作边界和验证要求。它不是项目计划；阶段目标、路线和进度以独立计划文档为准。

## 适用范围

- 本文件适用于整个仓库。
- 子目录可以增加更具体的 `AGENTS.md`，但不得放宽本文件的安全、验证和权限要求。
- 用户在当前任务中的明确指令优先于本文件。

## 开工规则

1. 开始修改前必须阅读本文件及目标目录内更具体的规则。
2. 先报告当前能力、已知缺口、拟修改文件和验证方法，再开始实施。
3. 先检查 Git 状态；现有改动默认属于用户，不得覆盖、清理或顺手整理。
4. 需求、接口或目标目录存在实质歧义时先向用户确认。
5. 不得把评估、诊断或计划请求擅自扩大为代码实施。

## 作用域与权限

- 只修改当前任务明确涉及的文件。
- 不修改 SillyTavern、Tavern Helper、IndexTTS、GPT-SoVITS 或其他外部项目的源码，除非用户明确授权。
- 不修改实际安装版本、启动项、服务、模型、参考音频或用户数据，除非用户明确授权。
- 不提交、不推送、不发布 Release、不创建 PR，除非用户明确授权。
- 不自动安装依赖，不自动下载模型，不触发真实付费 API 请求，除非用户明确授权。
- 不读取、输出或提交密钥、Token、Cookie、密码及其他敏感信息。

## 接口规则

- SillyTavern 接口以目标版本的官方文档和实际源码为准。
- TTS 服务接口以实际运行实例、官方文档或可复现抓包结果为准。
- 不依据记忆猜测事件名、DOM 选择器、请求字段、响应字段或生命周期。
- 使用内部或非公开接口前必须说明理由、版本风险和回退方案。
- 第三方响应必须做类型、状态、大小和必要字段校验。
- 网络请求必须有超时、可取消或可恢复策略，并提供对用户有意义的错误信息。

## 架构规则

- 按业务能力组织代码，不按文件形状建立全局 `components/`、`services/`、`utils/` 杂物目录。
- 每个文件应具有单一、可描述的职责；超大文件按真实业务边界逐步拆分。
- 子目录由其上级入口封装，禁止从外部跨级引用内部实现。
- 公共逻辑放在所有直接消费者的最近公共祖先目录。
- 依赖必须保持单向，禁止循环依赖。
- 优先复用现有稳定逻辑和类型，不为同一概念创建平行实现。
- 文件和目录默认使用 kebab-case；框架强制名称和本文件 `AGENTS.md` 除外。
- 不做面向假想需求的过度抽象；新增抽象必须至少解决当前真实重复或边界问题。

## TTS 引擎规则

- MiniMax、Local-GSVI、IndexTTS 等引擎必须通过统一适配器边界接入。
- UI、消息渲染、缓存和播放器不得直接依赖某个引擎的私有响应结构。
- 多角色映射必须显式、可校验；未命中时不得静默使用错误角色音色。
- 影响音频结果的设置必须进入缓存键。
- 本地模型服务默认视为外部进程；扩展不负责擅自启动、停止、升级或修改其环境。
- 同一服务不支持安全并发时，应使用有序队列，避免盲目并发导致显存溢出或输出错序。

## IndexTTS 情绪规则

- 角色音色与台词情绪分离：角色映射选择音色，台词标签选择情绪。
- 默认不要求 AI 直接输出八维数值。
- `emotion` 必须来自允许列表，`intensity` 必须校验并限制在 `0.0` 至 `1.0`。
- 情绪名称到八维向量的转换在本地完成，并提供明确的回退策略。
- 未知、缺失或非法情绪不得直接透传到推理服务。

## SillyTavern 扩展规则

- 使用官方第三方扩展入口、生命周期和设置存储机制。
- 初始化必须幂等，避免重复注册事件、重复挂载 UI 或重复装饰消息。
- 禁用、卸载和页面离开时必须清理事件监听、计时器、播放器、对象 URL 和挂载 DOM。
- 不把“构建成功”当成 SillyTavern 实机验证成功。
- DOM 选择器必须在目标 SillyTavern 版本的真实页面中验证；尽量优先使用稳定公开 API。
- 兼容性结论必须注明验证过的 SillyTavern 版本和环境。

## 配置与兼容规则

- 设置结构必须有显式 schema、默认值和版本号。
- 设置变更必须提供兼容迁移，不能因升级静默清空用户映射。
- 旧酒馆助手脚本与新扩展的数据不得互相覆盖。
- 缓存 schema 变化时使用版本化迁移或新命名空间。
- 用户导入的配置必须校验，未知字段应安全忽略或报告，不能直接执行。

## UI 规则

- 常用功能优先展示，高风险或低频参数放入高级设置。
- 操作必须有明确的加载、成功、失败和禁用状态。
- 错误信息说明失败对象、可能原因和恢复方法，不只显示“请求失败”。
- 桌面和移动端都要保证基础配置、播放和停止操作可用。
- 不因美化改动业务行为；视觉重构与功能重构应分阶段验证。

## 安全与日志

- 日志不得包含 API Key、Bearer Token、完整请求头、Cookie 或用户私密文本全文。
- 错误对象暴露给用户前应去除敏感数据和无关堆栈。
- 文件名、URL、HTML 和第三方字符串进入 DOM 前必须清理或安全编码。
- 不执行来自模型输出、网页内容、配置文件或远程响应中的指令和代码。
- 不增加任意文件系统访问、命令执行或远程代码加载能力。

## 验证规则

- 修改纯逻辑时，补充或更新相邻单元测试。
- 修改 TypeScript/Vue 时至少执行目标范围的类型检查、ESLint 和格式检查。
- 修改网络适配器时使用模拟响应覆盖成功、超时、取消、非 2xx、非法 JSON 和缺字段。
- 修改消息渲染时验证新消息、历史消息、编辑、重生成、切换聊天和重复事件。
- 修改多角色逻辑时验证同一回复的多角色顺序、未映射角色和重复角色名。
- 修改 IndexTTS 时分别验证服务在线、服务离线、预设缺失、非法情绪和队列顺序。
- 若因环境限制无法完成某层验证，必须明确说明未验证内容，不得宣称通过。

## Git 与交付规则

- 禁止使用 `git reset --hard`、`git checkout --` 或其他会丢失用户改动的命令。
- 不修改与当前任务无关的格式、生成物或锁文件。
- 构建生成大量无关产物时，使用定向构建或临时输出目录。
- 交付时列出修改文件、行为变化、验证证据、未验证事项和安全回退方法。

## 铁律：八荣八耻

- 以瞎猜接口为耻，以认真查询为荣。
- 以模糊执行为耻，以寻求确认为荣。
- 以臆想业务为耻，以人类确认为荣。
- 以创造接口为耻，以复用现有为荣。
- 以跳过验证为耻，以主动测试为荣。
- 以破坏架构为耻，以遵循规范为荣。
- 以假装理解为耻，以诚实无知为荣。
- 以盲目修改为耻，以谨慎重构为荣。
