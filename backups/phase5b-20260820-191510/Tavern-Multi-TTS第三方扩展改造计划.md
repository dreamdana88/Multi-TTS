- MiniMax 云端 TTS。
- Local-GSVI 本地推理。
- `<say char="角色名">...</say>` 台词解析。
- 多角色音色映射。
- 提示词注入。
- 音频预取、缓存、播放与下载。
- 映射存档和测试语音。

## 2. 改造目标

将 Tavern Multi-TTS 从依赖酒馆助手运行时的脚本，迁移为可通过 Git 仓库地址安装、启停和更新的 SillyTavern 第三方前端扩展。

目标包括：

1. 保留现有 MiniMax 与 Local-GSVI 功能和用户配置能力。
2. 新增 IndexTTS-2.5 本地引擎。
3. 保留并增强多角色音色映射。
4. IndexTTS 采用“角色绑定音色预设，台词按需携带稀疏命名情绪”的设计。
5. 将大文件按业务边界拆分，降低修改和排错成本。
6. 建立可重复的构建、静态检查和测试流程。
7. 迁移期间保留旧酒馆助手脚本作为稳定回退版本。

## 3. 非目标

第一阶段不处理以下内容：

- 不修改 IndexTTS、GPT-SoVITS 或 SillyTavern 本体源码。
- 不把 Python 模型环境打包进扩展。
- 不开发必须安装的 SillyTavern 服务端插件。
- 不承诺真正的流式音频；首版仍以完整 WAV/音频结果播放为准。
- 不在功能迁移完成前删除或停用旧酒馆助手脚本。
- 不提供旧酒馆助手脚本设置到新扩展的自动导入或兼容迁移；新扩展配置由用户在新面板中手工填写。
- 不建立本地情绪模板、情绪模板编辑器或命名情绪到复合向量的模板表。
- 不要求 AI 记忆或直接输出 IndexTTS 八维数组的位置顺序。
- 不在未经确认时提交、推送、发布 Release 或替换实际安装版本。

## 4. 总体设计

### 4.1 运行链路

```text
SillyTavern 消息事件
  -> 解析 <say> 台词
  -> 根据 char 查找角色映射
  -> 选择 TTS 引擎与角色音色
  -> 解析可选的 emo="情绪名:数值"
  -> 请求对应 TTS 服务
  -> 写入浏览器音频缓存
  -> 在消息中提供播放与下载控件
```

### 4.2 引擎统一接口

每个引擎实现统一能力契约，避免 UI、消息渲染器直接判断不同接口细节。

建议的概念接口：

```ts
interface TtsEngineAdapter {
  readonly id: string;
  checkHealth(): Promise<EngineHealth>;
  listVoices(): Promise<VoiceDescriptor[]>;
  synthesize(request: SynthesisRequest): Promise<Blob>;
}
```

实际字段必须以现有代码和目标服务的真实接口为准，实施时不得凭计划文本臆造。

### 4.3 目录原则

- 按业务能力组织文件，不建立项目级 `components/`、`services/`、`utils/` 杂物箱。
- 引擎内部实现由引擎入口文件封装，外层不得跨级引用内部文件。
- 公共类型和逻辑放在多个直接消费者的最近公共目录。
- 依赖保持单向，禁止循环引用。
- 文件和目录使用 kebab-case；SillyTavern 规定的入口文件名除外。

建议初始结构如下，实施时可依据真实代码调整：

```text

│  ├─ extension.ts
│  ├─ extension-settings.ts
│  ├─ engines.ts
│  ├─ engines/

│  │  ├─ local-gsvi.ts
│  │  └─ index-tts.ts

```

## 5. 多角色与情感设计

### 5.1 角色映射

每个酒馆角色可以绑定：

- 引擎类型。
- 引擎音色标识。
- IndexTTS 音色预设。
- 默认语言。
- 可选的角色级生成参数覆盖。

未命中角色映射时使用引擎默认配置；没有安全默认值时应明确报错，不能静默选择错误音色。

### 5.2 IndexTTS 音色与情绪分离

IndexTTS 角色预设只负责稳定信息：

- 音色参考音频。
- 可选的情绪参考音频。
- 基础生成参数。

每句台词的情绪由标签动态决定，不为每种情绪复制一套角色预设。

日常、闲聊和平静叙述不携带情绪字段，继续使用“与音色参考音频相同”的普通生成方式：

```xml
<say char="真田幸影">今天要去哪里？</say>
```

只有出现明显情绪变化时才携带稀疏命名情绪：

```xml
<say char="真田幸影" emo="怒:0.35,厌恶:0.15">出去。</say>
```

职责分离如下：

```text
char  -> 选择角色音色预设
emo   -> 描述本句实际存在的情绪名称与强度
API   -> 将稀疏命名情绪转换为 IndexTTS 固定顺序的八维向量
```

### 5.3 情绪向量

允许的情绪名称与 IndexTTS WebUI 保持一致：

```text
喜、怒、哀、惧、厌恶、低落、惊喜、平静
```

标签格式：

```xml
<say char="水无濑寻" emo="喜:0.35,平静:0.10">今天心情还不错。</say>
```

约束如下：

- 没有 `emo` 时不得构造全零向量，而是使用“与音色参考音频相同”的普通生成方式。
- `emo` 只列出本句实际存在的情绪，未列出的维度由 API 补为 `0`。
- 一般只使用一种情绪；复合情绪最多允许两至三种，不开放更多组合。
- 日常轻微情绪建议使用 `0.10` 至 `0.35`，明显情绪建议使用 `0.35` 至 `0.60`。
- `0.80` 以上只用于重大情绪爆发，不应成为常规输出。
- 每个已输出情绪的值必须是大于 `0` 且不超过 `1.0` 的有限数字；不需要的情绪不输出名称和值。重复名称、未知名称、超过三种或非法数值均视为整段 `emo` 无效。
- 无效 `emo` 必须回退普通生成并记录警告，不得阻止台词生成，也不得沿用上一句情绪。
- 解析时可统一中英文冒号和逗号，但提示词只示范半角 `:` 和 `,`。
- 插件不得保存或提供本地情绪模板，不增加模板编辑、重置或导入导出界面。
- AI 不输出八位数组，也不需要知道各情绪在底层向量中的位置。
- IndexTTS API 接收经过结构化的情绪名称和值，并在服务端按固定顺序构造、校验和归一化八维向量。
- 情绪必须进入缓存键；同一文本、音色和语言但情绪不同，不得复用同一音频。

结构化 API 请求建议使用对象表达稀疏情绪，禁止依赖对象键顺序：

```json
{
  "emotion": {
    "喜": 0.35,
    "平静": 0.1
  }
}
```

该字段是现有语音请求的可选扩展；未提供时保持现有预设驱动行为。用于日常 RP 的音色预设应设为“与音色参考音频相同”，这样未携带 `emo` 的台词就是普通生成，同时仍保留其他预设使用情感参考音频的能力。

### Step 6：动态情绪向量

工作内容：

1. 先扩展 IndexTTS API，在现有语音请求中增加可选的结构化 `emotion` 对象；由服务端完成名称白名单、数值校验、固定顺序映射和向量归一化。
2. 扩展 `<say>` 解析器，只支持可选的 `emo="名称:数值,名称:数值"`；不增加 `emotion`、`intensity` 或原始八位数组语法。
3. 将合法稀疏情绪传给 IndexTTS 适配器，并以固定顺序规范化后加入缓存键。
4. 更新提示词注入：普通台词省略 `emo`，只有明显情绪变化才输出；一般最多一至三种，数值保持克制。
5. 增加缺省、单情绪、两至三种复合情绪、全半角标点、未知名称、重复名称、超过三种、非数字、越界数值和逐句恢复普通模式测试。
6. 不新增情绪设置面板、模板表、模板存档或角色级情绪配置。

验收：

- 同一角色、同一音色预设连续生成普通台词和不同情绪台词时，无需切换角色映射或复制音色预设。
- 未携带 `emo` 的台词使用“与音色参考音频相同”；携带合法 `emo` 的台词仅对本句启用八维向量。
- 下一句未携带 `emo` 时自动恢复普通生成，不继承上一句向量。
- `喜:0.35,平静:0.10` 能稳定映射到正确维度，AI 无需记忆八维顺序。
- 非法情绪输入不会导致请求崩溃、污染配置或阻止台词生成。
- 不同情绪请求具有不同缓存键；并发和逆序返回时仍绑定正确的消息、Swipe 与台词段落。

## 8. 安全与隐私

- API Key 不写入日志、URL、错误详情或仓库。
- 本地服务地址只按用户配置访问。
- 不自动上传参考音频到第三方服务。
- 第三方响应视为不可信输入，必须校验结构和大小。
- 下载文件名必须清理非法字符。
- 不允许远程内容改变扩展配置、删除本地文件或执行代码。

## 9. 回退方案

1. 旧酒馆助手脚本保持原样并保留可导入构建产物。
2. 新扩展使用独立设置命名空间和缓存版本。
3. 每个阶段形成独立、可审阅的变更，不混入无关项目修改。
4. 实机验证失败时停用新扩展并恢复旧脚本，不修改外部 TTS 环境。
5. 不使用破坏性 Git 操作回退用户已有变更。

## 10. 开工门槛

实施任何阶段前必须先完成：

1. 报告当前基线、差距、目标文件和拟修改范围。
2. 确认目标 SillyTavern 安装路径与版本。
3. 确认本阶段验收标准。
4. 确认不会覆盖用户正在使用的旧脚本。
5. 未得到用户明确授权，不进入下一阶段。
